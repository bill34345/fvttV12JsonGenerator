# dnd5e 6.0.6 runtime source candidate

This owner contains optional changes to the dnd5e 6.0.6 system source. It is not a Foundry module and does not patch a running prototype.

`upstream-lock.json` fixes the official commit and `module/tooltips.mjs` SHA-256. `patchTooltipLifecycle()` validates that source once, normalizes only line endings, and returns the patched source. Build integration must substitute this generated source at its original module path when running the official Rollup code build; do not edit the installed `dnd5e.mjs` bundle or the shared reference checkout by hand.

The patch keeps the hovered element across UUID lookup, rich HTML generation and the next animation frame. A cancelled or replaced hover no longer renders old content or positions a tooltip whose source element has disappeared. Normal tooltip content, HTML sanitization, classes and positioning remain upstream behavior.

Set `SYSTEM_RUNTIME_SOURCE_ROOT` to a clean checkout of [dnd5e release-6.0.6](https://github.com/foundryvtt/dnd5e/tree/87e94dbd9f930135e0694cd7e7d49f210603cd2c), then run `bun run test:system-tooltip`. It evaluates the actual original and patched class in an isolated VM. Original-source negative controls reproduce both captured exceptions; repaired cases cover cancellation, hover replacement and normal display.

Build with `bun run prepare:system-tooltip --source-root <clean-pinned-source-root> --official-system-root <official-system-root> --compiler-root <compiler-root> --output <new-absolute-output-root>`. The official system root needs `dnd5e.mjs`, `dnd5e-compiled.mjs.map`, and `system.json` from [dnd5e 6.0.6](https://github.com/foundryvtt/dnd5e/releases/tag/release-6.0.6). The compiler root must supply Rollup 4.62.2 and @rollup/plugin-node-resolve 16.0.3. The builder normalizes source CRLF to LF, reproduces the official bundle byte for byte before applying the source transformer, then produces the patched bundle, source map and local system manifest as a three-file delta. It neither installs files nor changes the shared reference checkout.

The local manifest is now 6.0.6+local.3. It preserves the prior Tooltip transformer and the `!this.system.isOnActivity` addition to the pinned `ActiveEffect5e.isExpiryTrackable` getter. An effect selected by an Item activity is a reusable profile; its Actor-applied copy has no Item activity reference and retains normal expiry eligibility. Disabled, compendium, unsaved, detached, ordinary non-activity Item effects and the existing `dnd5e.isTemporary` rule remain governed by the original conditions. Applied-enchantment source-predicate checks are distinct from a full runtime enchantment workflow.

Run `bun run test:system-activity-template-expiry` with `SYSTEM_EXPIRY_CORE_ROOT` pointing to an app root with the ActiveEffect source SHA-256 pinned in `activity-template-expiry-lock.json`. The source was recorded on Core 14.369 and also matches 14.368. The test evaluates the actual pinned Core eligibility getters, dnd5e model preparation/`isOnActivity`, and original/patched system getter, with small document-host bridges. Set `SYSTEM_EXPIRY_TEST_ORIGINAL=1` only for an explicit negative control: the Aim/Berserk profile requirements then fail on the original getter. The original `test:system-tooltip` suite remains an independent preservation check.

The inventory patch locks `module/applications/components/inventory.mjs` in `inventory-resize-lock.json` and schedules only its ResizeObserver callback through `requestAnimationFrame`. `_onResize` and its cached column-priority, width and section-minimum calculations remain byte-identical. The upstream element initializes one local observer in `connectedCallback` and has no disconnect lifecycle; the patch keeps this behavior without new pending-frame state. A queued callback can update its own detached cells, and the same observer remains available after reconnecting.

Run `bun run test:system-inventory-resize`. The suite evaluates the actual pinned InventoryElement class with a small DOM/observer/frame host. It demonstrates original synchronous layout writes, candidate next-frame writes, correct header/row columns while narrowing and widening, custom minimum widths and detach/reconnect behavior. `SYSTEM_INVENTORY_TEST_ORIGINAL=1` selects original-source negative controls. These are source-method scheduling/column checks, not a browser ResizeObserver-loop reproduction; native minimize/restore A/B and visible-column acceptance remain separate runtime gates.

The builder checks both official JS and source-map byte parity, then requires that only `module/tooltips.mjs`, `module/documents/active-effect.mjs` and `module/applications/components/inventory.mjs` differ in the candidate source map. Existing official baseline artifacts can supply the original-code input after verifying their recorded hashes. When the metadata input is projected from an accepted local.1 manifest with only its version reset to 6.0.6, record that derivation separately; it preserves existing local metadata and is not a claim that the manifest reproduces untouched upstream bytes. Do not copy a full installed system or any world to prepare this input.

Core treats the local version suffix as a system version change and can run its world/package model migration on the next launch; this was observed for local.1. It remains a deployment side effect of later local candidates. The builder does not launch or migrate a world.

Pass `--initiative-precheck` to the same build command to add the batch initiative fix. The delta checks whether a combatant already has a finite initiative before building its grouping key. The builder verifies the official baseline and checks `module/documents/combat.mjs` as the fourth changed source. The manifest remains byte-identical to the prior local.3 build, so use file hashes to distinguish the two candidates. Run `bun run test:system-initiative-precheck` for the fresh-roll, same-batch and existing-score cases. See the [combat compatibility review](../../../docs/reviews/2026-11-13-foundry-combat-compatibility.md) for the observed behavior and limits.
