# 2026-11-24 Boss 战提醒 0.5.0 浴血与退场复验

本地 ServerNext 30002 的独立世界 `boss-reminders-native-20261123`，Foundry 14.370、dnd5e 6.1.1、Monster Manual 1.4.0。候选 ZIP、安装文件和 HTTP 实际下发脚本的 SHA-256 均为 `83278EC55B88C083DD4AE6362FF67CBBA42576145D654316A52EAADBCD2AE386`。运行中的模组登记仍显示旧版本 0.2.0，包内 manifest 与实际下发脚本已另行核对。

## 浴血状态

- 在三只原版怪物的临时独立 Token 上，将 dnd5e 浴血阈值覆盖为 75%。黑布丁在 51/68 HP 获得原生标记并立即提示分裂。黏土魔像在 92/123 HP 获得标记，自己的下一回合开始才提示失心狂怒。狂战士在 50/67 HP 获得标记和持续能力卡，从卡片应用浴血狂热后，原生巨斧攻击和感知豁免均为优势。
- 狂战士同时拥有原生自动标记和手动强制标记时，治疗到满血只去掉自动标记。狂热保留，原生攻击和豁免仍有优势。点「恢复自动」后，最后一个标记和狂热一起消失，两种掷骰恢复普通。随后在满血时再次强制浴血，卡片可再次应用狂热，两种掷骰再次取得优势。
- 验收宏的首次探针把百分比字段误写成各自的绝对 HP。原始 `01`–`02` 回执保留用于追溯。以上结论采用统一写入 75 后的 `03`–`07` 回执。

## 原生归零和死亡顺序

只启用提醒和 Monster Manual。原版 2024 僵尸受到普通钝击归零后，待结算卡显示不死坚韧，死亡状态与战败标记均未写入。GM 按存活裁定将其恢复到 1 HP 后，待结算清除。再次归零时，点确认死亡后才有死亡与战败。原版巴洛炎魔归零即弹焚身爆，保留目标且可推进回合。点选原生豁免 Activity 后生成使用消息，仍留在场上待结算。之后点「处理完毕」才写入死亡、战败。本用例验收到 Activity 发起和待结算状态，未摆放模板或施加伤害。无归零或死亡能力的普通对照 NPC 仍走原生自动死亡。官方源、导入 Actor 与 Token 的 Item/Activity 前后比对通过。

另用一个临时 NPC 检验同一对象的两阶段处理。直接归零时，归零能力和明确配置「归零也触发」的浴血能力同卡，普通浴血能力未出现。打开归零特性、实际使用这一浴血 Activity 后，Token 仍未战败。点「确认死亡」才进入死亡能力卡，确实发起死亡 Activity 后仍留在场上，点「处理完毕」才按顺序写入死亡、战败。对应 `13`–`16` 回执。

## 本地 91 模组组合

按原清单启用 91 项，包含 Babele、Midi-QOL、DAE、Chris Premades、CAT、Monk’s Combat Details 与 Bloodsplats。原版中文僵尸归零后先弹不死坚韧，恢复到 1 HP 取消待结算，另一次归零在 GM 确认死亡后才标记死亡、战败、隐藏并出现血迹。原版中文巴洛炎魔归零弹焚身爆，跨回合保留已选目标，实际发起 Activity 后仍待结算，点「处理完毕」才放行退场。对应 `17`–`21` 回执。

- DAE 独立临时 NPC 同时有两个 `zeroHP` 效果。普通效果按 Midi 的归零时限正常到期。配置了 `flags.dae.deleteUuid` 指向该 NPC 自己 Token 的效果保留，Token 仍在场上且保持选中。发起死亡 Activity 后仍待结算。GM 点「处理完毕」后才看到该效果以 `midi-qol:zeroHP` 到期，随后 Token 被删除。对应 `22`–`25` 回执。
- Chris Premades／CAT 独立临时 NPC 的死亡能力绑定到 `useOnDeath`。零血阶段未自动执行。进入死亡阶段后，从「运行已配置自动化」实际执行此能力，产生一条使用消息和一个完成的 Midi workflow，Token 仍待结算。GM 收尾后才标记死亡、战败并隐藏，收尾后的二次读回没有重复执行。对应 `26`–`29` 回执。

全栈加载和使用期间，控制台记录了 Foundry MCP Bridge 的 WebSocket 连接失败、Monk’s Bloodsplats 对加载中对象写入 alpha 的报错，以及 `renderChatMessageHTML` 上一次 `ChatMessage5e` 接收者异常。原生对照曾在 `createChatMessage` 记录相似的接收者异常，随后实际焚身爆仍发起并获得使用回执。原生夹具和组合夹具已改为读取使用消息里的 Item UUID。控制台回执单独保存。本次按卡片、实际使用消息、状态和 Token 事件的顺序验收。
