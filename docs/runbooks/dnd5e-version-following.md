# dnd5e 双版本线：资料查询、版本比较与 Next 更新

## 选择版本线

- **5.x 固定线**：开发与验收固定 dnd5e 5.3.3，不因 6.x 更新而升级 Mirror。5.3.3 当前也是官方最新稳定 5.x；若官方以后补发 5.x，先单独核对，不自动跨系列。
- **6.x 跟随线**：ServerNext 使用官方最新稳定 6.x，不把某个补丁版本设为永久上限。排除 draft、prerelease、master／开发分支及 7.x。
- V12 逐步弃用是已确定方向；本次不删除兼容代码或改变 CLI／Web 默认选择。正式生成器的现有 5.3.3 projector／来源验收不自动等于支持所有 6.x。

## 开工时的最短流程

1. 任务先写清 5.x 或 6.x、目标实例及行为出口。5.x 的目标就是 5.3.3；6.x 从[官方发布 API](https://api.github.com/repos/foundryvtt/dnd5e/releases?per_page=100)选最新非 draft、非 prerelease 的 `release-6.*`，按版本号比较。这里的“最新”来自官方发布，不来自 Context7 排序。
2. 读取对应本地 `system.json`，涉及运行任务还核对正常客户端的实际版本、Core、world、dataPath、端口／PID和服务共用情况。不能拿源码缓存版本当作已安装版本。
3. 以确定后的精确目标查询 Context7：5.x 写 `release-5.3.3`；6.x 写本次官方稳定 tag，例如 `release-6.0.5`，同时限定单一接口问题。结果必须检查引用来源；如果仍是 Wiki、master、6.0.x 或其他版本，只作为导航，回到目标 tag／提交的本地源码确认。
4. Next 系统落后时，在本 thread 已明确的本地 6.x 跟随授权内，先完成系统更新和针对性验收，再开始依赖该版本的新开发。不因“文档较新”直接更新系统；先核官方稳定发布、Core 要求、当前已启用模块全集的 manifest 范围、代码版本门／本地适配及真实服务归属；不能仅抽查几个关键模块。
5. 本地系统已有更新而缓存较旧，只补相应版本的源码资料；本地系统比发现结果新时重新检查发布来源，不自动降级。5.x 不因查询到了 6.x 片段而更新。
6. 记录当前实装系统、Core、固定源码提交、候选及本轮接受证据。精确版本记录服务于复现，不限制以后更新。历史 PASS 保留旧目标；影响明确且无变化的检查可复用，有变化的行为才重新核对。

## 已有资料如何复用

共享源码缓存由 `FVTT_REFERENCE_CACHE_ROOT` 定位，本机配置为 `F:/FoundryLab/reference-cache`；不同 worktree 复用同一套版本化资料，不各下载完整手册。

- 5.3.3：`dnd5e/5.3.3/repo`，由 `dnd5e-5.3.3` 清单登记。
- 当前官方稳定 6.x 的已取得源码：`dnd5e/6.0.6/repo`（2026-10-12取得），由 `dnd5e-current-6` 清单登记精确提交 `87e94dbd9f930135e0694cd7e7d49f210603cd2c`。取得资料不表示Next已更新；本批取得时Next仍6.0.5，模块兼容前置和运行接受见本批预检记录。下一次升级同时更新该条目的 revision／target，而非永久固定补丁版本。
- `references/dnd5e-6-current/system.json` 是对应官方发布清单，说明取得的目标，不证明 Next 已完成安装。
- 本机旧 Foundry API 镜像 `14.361` 仅作导航；精确 Core 行为核对实际安装源码及发布说明。

离线校验使用 `bun run references verify`。现有 CLI 校验整个清单，不提供按额外位置参数筛选的保证。

当前 bootstrap 在替换已有缓存时会临时移动旧目录；它不能用作本项目无备份规则下的已有缓存升级路径。只在目标全部不存在的首次获取中评估它。更新已有共享资料时先核源仓库和旧 checkout 干净，获取官方固定 tag 后创建新的版本化引用 checkout，可复用 Git 对象；不复制整个 dirty 工作区，不改变旧版本 HEAD。此前用既有6.0.2对象取得6.0.5，本批再由干净6.0.5引用获取固定6.0.6；这些checkout是各版本源码资料，不作为运行实例或回滚备份。

## 系统更新的范围和验收

使用正常 Setup 系统更新入口，只处理 ServerNext 的 dnd5e。维护前保存必要清单、版本与来源字段的读回证据，不创建世界／安装目录备份；不直接编辑运行中 LevelDB，不连带升级 Core、Mirror 或生产。

检查发行说明与当前已启用模块全集，包含自有模块代码中精确版本比较；6.0.x 修补以正常启动、受影响代表行为及必要持久化核对为主，不默认重跑整个迁移或全模块矩阵。6.1／6.2 若改变接口或增加功能，按实际影响扩大检查。普通更新无需重新决定“要不要跟随6”；需要 Core 更新、跨7、共享服务协调或处理数据异常时，按具体问题处理，不静默扩大范围。

Context7 检索、源码取得、包安装、客户端启用、功能接受和资源清理分别报告。一个层级通过不能替另一个层级；现有专属 adapter／收据的旧版本身份不会自动变成新版本接受。

## 接续与检查时机

每次开始与系统版本相关的开发或维护时做一次官方／本地比较。没有新目标或变化证据，不重复取得缓存、重放迁移或重复浏览器场景。

本流程没有安装后台定时任务，不能保证在发布瞬间自动发现更新。若以后明确设置监测频率，应使用宿主原生 automation；不要由 Chrome 执行聊天轮询，不建立 watcher 等待浏览器回调。

执行依据见[本次版本策略和核查记录](../reviews/2026-10-01-dnd5e-version-following-policy.md)、[开发反馈闭环](development-feedback-loop.md)与[资料路由](foundry-v14-development-source-routing.md)。

本次反例：系统6.0.2→6.0.5安装成功，但10个自有模块因maximum=6.0.2被自动停用，其中至少5个还有运行代码版本门。不能改高清单上限后就宣称兼容；按新增模块范围处理适配、原开关恢复及受影响行为，未闭合前报告系统已安装／模块组合未接受。
