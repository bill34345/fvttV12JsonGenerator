# Forge 分步 API 与逐步核验：可行性判断

日期：2026-10-13。状态：建议方案，尚未实施、尚未验收。本记录回应用户提出的先翻译、基础数据与特性分开处理、动作拆分、每步返回后检查。没有启动新一轮生成、修改生产代码或改变上一批六例0/6的结果。

## 判断与现有证据

可以采用固定步骤的小任务调用，并在步骤之间执行程序检查。拆分应按数据职责与完整能力边界进行，不能只增加请求次数或按字符数把一句规则切碎。它能减少单次任务混杂、提供明确失败位置，但不能自行修复程序丢文、来源证明消费不一致及错误的条件校验。

本地核对：

- [Forge 正式流程](../../packages/forge-browser-runtime/src/encounterIntake.ts) 已有发现、提取、配置、中文阶段；并非完全只有一次调用。
- [浏览器提取入口](../../packages/forge-browser-runtime/src/ai.ts) 的 `counted.extract` 仍一次接收整只怪的来源并返回完整 IR；基础字段、全部特性和动作以及来源证据仍集中在这次输出。
- [中文请求入口](../../packages/generation/src/reviewed-localization.ts) 的 `presentationTexts` 从 Actor 字段与已建立的呈现计划提取待译内容。没有进入这些字段的来源正文，不会自动进入翻译请求。
- [完整规则证据入口](../../packages/intake-ai/src/source-completeness.ts) 仍按单个 coverage 候选证明完整能力；多次 API 调用不能修复这一消费约定。
- [六例实际报告](../acceptance/2026-10-13-forge-six-fresh-retest.md) 保存丢文、分段证明、条件语义、排版及真实模型字段错误。17次请求均有完整回复；当前证据没有证明请求次数不足或长上下文容量是主因。

“任务混杂应当拆分”是依据接口职责与失败输入提出的设计判断；分步改造能够提高多少成功率、耗时与费用尚未测量。

## 建议步骤及检查出口

| 步骤 | 模型或程序的职责 | 返回后检查 |
|---|---|---|
| 来源分单元 | 程序保存原文，划分基础数据、外貌及每项完整能力；边界不明时显式待审。原始位置、编号与哈希由程序持有。 | 每段内容有单元归属；无删文、重复或跨能力吞并。显示时的排版规范化保留到原文的映射。 |
| 英文转中文草稿 | 对稳定单元生成对应中文草稿，先提供可读内容；英文原文永久保留并参与后续核对。 | 对照每个单元的数字、公式、单位与术语；自由文本语义仍可能需要 GM 核对，不能以字段检查宣称语义全对。 |
| 基础数据 | 单独提取 AC、HP、六属性、速度、感官、抗性、语言等；已登记枚举由程序映射。 | 逐字段对照原文；尺寸附注、外貌等没有原生字段的内容仍须进入明确文本去向。 |
| 完整特性与动作 | 每次一项完整能力，或少量短且独立的完整能力。返回目标、触发、攻击或豁免、伤害关系、状态、资源与期限等事实。 | 对照完整规则的“目标—条件—结果—期限”；缺文、否定、DC、属性、伤害关系冲突继续拒绝。 |
| 合并与生成 | 程序合并通过核对的事实，仅归一化一次；Actor、已支持规则的固定中文和 GM 说明共同消费。 | 核对跨能力引用、共享规则、全部来源去向、事实与 Actor 投影及中文块参数。未知机制保留完整来源与待审状态。 |
| 图标与导入候选 | 基于已核实机制执行既有模糊、类别与继承选图，生成完整预览。 | 每个 Item/Activity 为可解释的非默认目录图；审批、保存读回与原生导入刷新仍走既有门禁。 |

英文可以先翻译，但初稿不是唯一机械事实来源。若先把英文翻错，再仅根据中文生成数据，会把同一错误传递到后面。建议保留单元级中英对应，机械事实仍核对原文；已支持的最终中文规则由核实后的事实生成。初稿中的对应叙事文本可作为剩余文本槽候选，最终仍须核对身份和内容，不重复让模型重写固定机械规则。

动作拆分保留完整上下文。例如一项能力引用公共射程、可见目标或选择多个射线时，每个子项都需携带公共规则；多重攻击、传奇动作成本和资源共用也需在合并阶段核对。不能把伤害留给一次调用、减半前提留给另一次，再让模型自由拼接。

## 每步核验及失败处理

- 步骤返回后自动执行程序检查、保存来源身份、输入、回复、结果和错误位置。程序检查不能以模型回复“正确”替代；不要求用户逐步确认。
- 检查成功的步骤只允许在来源、模型配置、模板与规则版本身份保持时复用；不得把过期批准沿用到新结果。
- 单次提交中的计划步骤调用与失败重试分别计数。沿用既有有限修复上限，不增加外层重复生成，不用更多调用掩盖首次失败。
- 保留失败步骤和已成功步骤的现场。需要明确后续尝试时单独记账，不把再运行结果改写成首次成功。
- 先将本批保存失败作为离线正式链输入，证明正常及等价表示通过、真实缺文与冲突仍拒绝；再冻结版本做预先固定新来源的首次生成及必要原生验收。已有六例记录不改写。

调用量可能增加，耗时和费用不保证下降。优先由程序处理位置、编号、精确原文、已登记规则与固定说明，把模型调用留给确需语言理解的工作；不能把每个数字都拆成一次请求。

## 外部资料与适用边界

1. Anthropic 的 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 描述固定子任务串联及中间程序门禁，指出这种方式以延迟换取任务专注，并要求用评估证明新增复杂度的价值。这支持分步模式，不证明 Forge 已可靠。
2. Google LangExtract 的 [长文本示例](https://github.com/google/langextract/blob/main/docs/examples/longer_text_example.md) 采用保留上下文边界的分块及来源关联。其多轮提取策略不直接采用，本任务保持既有首次提交及有限修复边界。
3. 一手用户报告 [LangExtract #545](https://github.com/google/langextract/issues/545)（2026-09-23）记录将23类实体分成3次提取以控制输出长度，也记录继续缩小块仍可能解析失败、调用量反而增加。报告是约16万字符的金融 PDF，模型与 Forge 不同；不将其数值或成效推广到本地几千字符的怪物资料，不采用其过滤丢弃正文的做法。该功能请求打开时仍为 Open，没有把请求当作库中已经发布的修复。

调研使用 AnySearch 的 code 子域发现、文档与混合检索；其 Anthropic 正文提取返回空内容，已改用网页读取核对原始正文，并读取上述 GitHub 原始问题。没有以二手教程或搜索摘要代替结论依据。

## 待判断引入、本地化与候选复查

- 当前只建议借鉴固定步骤、完整单元、来源关联和程序门禁，不引入新模型服务、框架或 LangExtract 依赖，不升级公开 Forge 协议。
- 新候选复查：先固定其源码版本、输入输出与错误处理，再用本地来源丢文、同能力分段、共享目标、条件减半及真实模型错误作反证；不满足完整保留与严格校验就不接入。
- 仍未证明：分步方案对 Forge 的首次成功率、跨 PDF 表现、成本与耗时；需要实施后的对照证据。

本记录为内部设计调研，未改变当前用户入口、支持范围、步骤或发布状态，无需为未实现方案刷新产品手册。
