# WMP 收尾后的开发流程复盘与提速方案

日期：2026-09-29。性质：证据审计、架构建议与候选规范；不是新一轮玩法验收。旧的 [9/28 审计](2026-09-28-custom-module-delivery-adversarial-audit.md)保留，本报告以它为基点，复查后续接管中的错误，并加入 ServerNext 对照与外部反证。

## 1. 结论与责任

主要问题在代理的工作方法和工程反馈，不在用户缺少一条“神奇 prompt”。我作为 WMP 接管主控，没有充分做到：把读过的上游变成实现约束；怀疑自己的测试模型；准备好工具再交给执行者；及时撤销错误验收条件；让新线程能从一个可靠的当前状态继续。Astra/max 没有抵消这些失误。用更强的推理、更多测试数量或更长对话替代真实接口事实，都没有成立。

本轮最重要的修正是：**并非从未读过上游，而是没有及时用对读到的东西。** 9/22 已实际读取 wm5e 固定版本，9/26 也读过 AC5e；9/29 对照实际攻击输入时序并修正模拟测试后，原生 Vex 两击通过。因此“每次都上网搜索”不够，必须让研究产出一条可验证的接口事实和相应检查。[WMP 原始事件审计](2026-09-29-workflow-audit-evidence/wmp-process.md)

用户观察到最后半天推进明显加快，有记录支持：9/29 15:16 再次催促借鉴，到 15:46 报原生 Vex 通过、22:00 本地交付，约 30 分钟及 6 小时 45 分钟。不能把它说成提速倍数：部分窗口修复发生在催促之前，Fatal、生成导入及集成检查也已先完成。更早的 Lab 占用、明确暂停和正式浏览器权限拒绝同样不能计成连续开发工时。

本报告不把责任平分。用户已经明确的自有实现、借鉴上游、独立 Chrome 线程、复用测试对象、不要无意义长测，均不属于坏 prompt。用户表达中确有几处可以更早澄清的歧义，单列于第 7 节。

## 3. 可以确认的失误，以及最早应在哪里阻止

| 失误 | 原始事实与后果 | 应改变的机制 |
| --- | --- | --- |
| 把自己的模型当成真实接口 | WMP 模拟测试先 configure 再 hook，实际顺序相反；AC5e 早期已捕获输入，WMP 晚补优势无效。大量单测绿色未发现。 | 新外部接口先做真实版本契约检查；保存事件顺序，再据此建立 mock。 |
| 围绕不完整证据重复战斗 | 首击证据迟到；历史 ticket 被当实时预约；导出分类、保存成功、当前状态混在一起。 | 每个关键状态立即留原件；行为、证据、清理分开；已有原件足够时修关联器，不重打。 |
| 主控派发了尚不可用的工具 | 本线程语法检查 exit 1 后仍派发；宏序列化导致空文本框；后续派发缺绝对路径，让执行者去 master 查不存在的文件。 | 检查结果必须控制派发；新工具先做最小显示／导出／读回；合同自带完整路径和身份。 |
| 主控创造了不存在的前置条件 | 要求旧聊天卡随新目标选择更新，后来源码证明目标在创建卡时固化。 | 每个阻断条件必须有产品要求或真实协议根据；假设被推翻时明确撤销，不能继续等。 |
| 违反已读的协作约定 | 9/26 已读不得轮询规则后，记录有 370 次 wait_threads 请求，326 次可确认超时；还发生子代理替代独立线程、回调主控串线。 | 采用准确线程 UUID、dispatchId、持久当前合同与一次回执；没有独立工作时结束回合。超时不一律等于没有新进度，不能把次数直接换算浪费。 |
| 迁移的任务全集不完整 | ServerNext 85 项表只由已装＋计划包构成，遗漏旧世界启用差集中的 24 项。表内完成不等于迁移完成。 | 分母从源世界事实生成，每项有保留／替换／退役／暂缓决定；不要硬编码“总共85项”。 |
| 阅读遗漏被包装成外部阻塞 | CE 同一 v9.2.7 发行说明已经写 D&D6 支持，旧报告却称没有依据、置 HOLD。 | 对“不支持／需等上游”的否定结论复核原文及版本；未验证与已不支持分开。 |
| 另一项目重复相同测试盲点 | Item Piles 六项离线测试 await 自建注册表；真实 hook 同步返回，消费者先缓存旧集成，实机出现字段和容器转移错误。 | 测一次真正的“注册→首次消费→缓存”边界，不能仅验证理想配置对象。 |

这些结论分别有原始请求／结果、补丁或 JSON 支持，详见两个取证附件。截图错位的历史情况只核对了当时父审纠正记录，本次未重新视检旧图。旧审计关于通知失败可能影响提交结果的静态风险，也不能升级为“Vex 实际根因”。

已经有效的设计需要保留：纯规则层、版本化契约、稳定攻击 ID、GM 权威、固定构建身份、持久测试批次、按影响复验和必要的真实玩法证据。WMP 当前已有两击测试、收据 CLI 和关联器；方案不是再从零写这些东西。

## 4. token 能说明什么

按逐响应 `token_usage_record` 去重统计，不相加会话延续文件里的累计快照；缓存包含于输入，reasoning 包含于输出。

| 有限样本 | 唯一响应数 | 累计处理 token | 其中缓存输入 | 未缓存输入＋输出 |
| --- | ---: | ---: | ---: | ---: |
| WMP 指定六文件 | 8,246 | 2,578,335,492 | 2,541,155,456 | 37,180,036 |
| ServerNext 指定十文件 | 9,918 | 2,886,526,368 | 2,843,870,336 | 42,656,032 |

来源与统计边界：[WMP metrics](2026-09-29-workflow-audit-evidence/wmp-metrics.json)、[ServerNext metrics](2026-09-29-workflow-audit-evidence/servernext-metrics.json)。不是所有旧子任务的完整成本，不是账单、订阅额度或“全部浪费”；不能把两行当已测出的节约空间，也不能从缓存比例推断速度。没有足够数据量化每个错误耗了多少额度。

已有事实仍足够指导修复：同一事实多次转抄、主控反复查子线程、工具错误引发业务重验、过长上下文保存操作状态，都是应减少的重复工作。下一步要测的是**同样验收标准下的一件工作总成本**，包含父任务、执行者、返工与用户救场。

## 6. 应怎样改架构与 E2E

### 6.1 一个小型共用基础，每个模块补自己的案例

对“每个 mod／worktree 要不要先做测试工具”的回答：**先有能跑通一条真实链的最小检查能力；共用能力逐步提取，模块只写自己的准备和判断。** 不给每个 worktree 造一套框架，也不要求先完成万能平台才开始业务。

| 层 | 负责什么 | 本项目落点 |
| --- | --- | --- |
| 纯规则 | 输入、状态转移、幂等、数值边界 | 保留 WMP `src/core` 等既有边界。 |
| 精确版本适配 | hook 顺序、文档差异、消息、权限、注册及缓存 | 在既有 adapters 附近补真实协议检查，异常返回可区分原因。 |
| 共用验收基础 | 环境身份、任务专属对象、步骤关联、收据保存／解析、恢复及清理 | 从 Foundry Ops、WMP harness／receipt CLI 提取已重复能力；两个真实消费者成立后再固化 API。 |
| 模块案例 | 正式入口、前置、期待的语义、独立判定 | WMP 的首击效果→次击消费→再授予；ServerNext 的完整清单、版本支持、注册和容器／物品迁移。 |
| 浏览器执行 | 少量必须亲眼验证的用户动作、窗口、拖放、角色差异 | 按获准的 Chrome 工具与委派路径执行；不代替文件转抄或所有规则组合测试。 |

当前 WMP `src/index.ts` 直接引入 `e2e-harness.ts`，所以改测试界面也会改变 runtime bundle。这是后续可拆的实际边界，不是立即重构两千行 runtime 的理由。先把文件侧收据、状态和判定与业务代码分开；确需分离浏览器 harness 时再设计受控开发入口。行为资源、运行环境、验收工具各有版本身份，**不能靠忽略哈希差异免测**；是否复用旧 PASS 仍需明确影响关系。

正常使用手册只描述产品行为，测试进度放一个当前状态记录。规范／工具尽量形成独立可审查增量，避免被大型 mod 最后一个 case 卡住。但已有 dirty 成果不能擅自复制整合；发布仍需原有授权。

### 6.2 一次验证的顺序

1. 说明完成意味着什么，核对目标和真实前置。
2. 查已有实现／精确版本，将关键事实变成一个可推翻假设的窄检查。
3. 完成一个小的真实链路，再扩展同类规则；已有 mock 按真实记录校准。
4. 失败先分清工具、环境、协议、业务、证据还是授权；同一失败两次没有新信息，停止原路尝试并换诊断方法。
5. 规则组合留在低层；浏览器保留代表性用户行为与跨客户端问题；只重验被修改影响或证据不足的部分。
6. 从同一份原始收据生成结论与简报；行为、证据、清理分别判定，父审不能仅看 PASS 标签。

“保持怀疑”针对未证明的接口、否定结论和相互矛盾的证据；不意味着反复怀疑未变化且已经充分验收的事实。

### 6.3 没有可借鉴项目时

没有上游不是无限尝试的理由。先列最小状态变化和不变量，再列两个会导致不同观察结果的解释，用一个小实验区分。例如：到底是优势输入在窗口创建前就丢了，还是消费状态没有解除？记录同一次攻击的输入和状态转移，比不断换窗口选项更能回答问题。

同一路线两次无新信息之后，下一动作必须是缩小复现、读取精确平台实现、改变探针或请求独立反驳；不能继续同样补丁再完整 E2E。仍缺产品语义才问用户；技术事实由代理继续查。不能保证每项创新都快，但可以确保失败会产生可定位的材料，而不是再耗几天仍不知道卡在哪里。

## 7. prompt 单独复盘：应该问什么，不该让用户承担什么

| 实际表达／情境 | 责任判断与今后做法 |
| --- | --- |
| “借鉴上游，但最终全部在自己的 mod” | 已明确。我曾误解成依赖上游交付，是我的理解错误；不能再要求用户澄清同一决定。 |
| 询问“原始已接受 enriched source 在哪个路径”，用户答“没有” | 问句混合术语、存在性和路径，代理不能推断整个项目没有来源。先查仓库与既有锁定记录，仍有歧义才问“是没有现成路径，还是此前就没有该资料”。 |
| “全部／做完／结束”没有已知验收出口 | 若会影响本地交付、支持版本、生产安装或合并，先用具体选项问清；已有明确出口则沿用。不能把“继续完成”擅自转成发布权。 |
| “不需要测试官方支持的 mod” | 根据上下文明确为安装、启用和新增错误读回；本地改造关键路径另有语义检查。若上下文不足，问验收层级，不自行扩成全玩法矩阵。 |
| 期限或“别停” | 接受优先级压力，但不把它变成少验／伪报 PASS，也不添加无关工作保持活跃。只有会改变验收出口时需要问取舍。 |
| 多次调整优先级、暂停／恢复、后来取消时间上限 | 合法变更，更新当前合同并标旧指令被替代。ServerNext 有一次后续明确批准30分钟子计划，不能把那次约束都说成代理继承旧规。 |

用户不需要每次写一份工程规格。一个足够好的起点是：“要得到什么、在哪个环境、哪些结果算完成、允许哪些外部改动；有改变结果的歧义先问我。”模型负责查路径／API、补计划、固定证据与执行检查。一次问1–3个真正改变结果的问题；不因内部技术不确定把设计工作退回给用户。

## 8. 让新线程继承改进，以及如何证明提速

本轮已经准备可审查的 [.ruler/AGENTS.md](../../.ruler/AGENTS.md) 小幅修订、[按需 runbook](../runbooks/development-feedback-loop.md)及[合同字段示例](../templates/development-task-contract.example.json)。Ruler 根说明同步生成。移除固定30分钟总上限遵从用户前述要求；单次操作超时和禁止无意义长测仍保留。

这些目前只在审计 worktree，**还不是所有新线程的默认基线**。可靠继承需要把获准的规范／工具增量纳入已提交基线，并由新任务记录实际读到的版本。仅写在本聊天、追加 memory 或让模型承诺记住，均不足够。本轮不修改全局 skill／memory，也不越权合并。

落地顺序和验收表见[反馈工具试点计划](../plans/2026-09-29-development-feedback-pilot.md)。先用已保存的真实失败校验方案，再在下一件自然发生且已授权的工作中试用；不为证明新流程重新打完已完成 WMP，不跑四小时 soak。

本轮及首个试点保持用户要求的 Astra/max；先隔离流程变量。将来若用户允许比较 effort，使用相同任务边界与验收口径，统计所有父子任务、返工和人工介入。未经测量不宣布降档更省，也不拿另一旧模型的 high 经验代替本项目数据。

完成标准是下一批任务更早得到有用失败、重复准备／手填减少、合格交付时间与总处理量下降，并且没有增加漏验或缺陷。少量任务只能提供方向性数据；安全／权限及语义错误是硬失败，不能拿速度抵扣。
