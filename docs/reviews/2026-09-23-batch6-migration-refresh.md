## Observed `isDamaged` timing failure

In the 2026-09-23 AL Chrome E2E, a normal DAE Actor effect with `flags.dae.specialDuration=["isDamaged"]` added 10 walk. A real Midi attack against an owned token generated 13 piercing damage. Before the manual Midi chat-card APPLY, target HP was still 40, but the exact effect had already been removed and walk restored from 10 to 0. APPLY then changed HP 40→27. This fails an acceptance criterion that `isDamaged` should expire only after actual HP application. The owned Actor/Scene/Token fixture was cleaned and the shared combat/time/targets returned to its captured baseline. Evidence: `F:\FoundryLab\foundry-v14\evidence\server-next-migration\batch6AL-dae-isdamaged-20260923\batch6al-report.md`, `isdamaged-result.json`, original CUA record set `chrome-cua-raw.jsonl`.

Locked local.8 code makes the ordering plausible: `processDamageRoll` calculates `workflow.damageList` and calls `workflow.callDamageHooksAndMacros(...)` before creating the reverse damage card. That method removes effects bearing `isDamaged` when calculated `hpDamage` is nonzero. `WorkflowState_RollFinished` also calls `expireTargetEffects(["isDamaged", ...])`; with `autoApplyDamage="none"`, it tests the predicted `damageList.hpDamage`. The card's APPLY action later updates HP. Source: installed local.8 `midi-qol.js` around `processDamageRoll` line 15367, `callDamageHooksAndMacros` line 30939, `expireTargetEffects` line 28647, and `WorkflowState_RollFinished` line 28013. Static source establishes the order and conditions; the Chrome readback establishes the concrete timing. The installed source map ties this to `Workflow.ts:2384-2413,3030-3042,3773-3865,6575-6604` and `utils.ts:535-800`: the `isDamaged` hook and effect removal run while building projected damage before the manual card. The core dnd5e `Actor5e.applyDamage` resolves only after its document update. This source-defined timing explains the E2E without making the stronger after-HP criterion pass.

## Decision and localization queue

- `DAE isDamaged` with manual Midi APPLY: **FAIL for after-HP-application timing** under current `autoApplyDamage=none`; the existing code expires from a calculated damage event. Read-only tracing of the installed bundle source map confirms this source-defined event is calculated positive damage before the manual card applies HP, not an actual post-HP-write event. The narrower calculation-triggered behavior is verified, while the post-application criterion remains FAIL. A post-HP semantics change would require a separate Midi repair across automatic/manual apply, cancelled cards, temporary HP, zero damage, multi-target and undo. Do not relabel the AL failure as PASS or change global damage settings. Do not change world-wide autoApplyDamage merely to make a test pass.
- AC5e 14.603.2: **installed and client-recognized; activation/migration/gameplay NOT_EXECUTED** on ServerNext. Read-only Chrome audited the world before activation: old AC5e was inactive and `core.moduleConfiguration` was false; `lastMigratedPoint` was absent/unregistered. Its locked migration guard will likely run when enabled, but a scan of 285 world Actors and 180 world Items found zero ActiveEffect changes with the old range subkeys targeted by that migration. The official package was then installed and loaded through a normal Setup round trip while Node PID and loopback listener remained. AP saw 14.603.2 still unchecked but could not read the exact client baseline with its accessibility-only interface; it made no setting change. A new AQ task confirmed that the current official Chrome CUA tab exposes an origin-scoped CDP read-only capability, then verified the sole GM and exact scene/combat/time/counts/targets/workflow/chat baseline. It again found AC inactive, its world setting false, and the migration marker absent. Thus the AP inspection capability gap is resolved; enablement remains a separate normal Module Management UI round, followed by migration readback and owned-fixture condition roll, target/range, damage, and Midi local.8 bridge checks. Evidence: `F:\FoundryLab\foundry-v14\evidence\server-next-migration\batch6AP-ac-enable-20260923` and `batch6AQ-ac-readback-20260923`.
- Token Action HUD D&D5e and Plutonium CN remain the earlier documented `BLOCKED` candidates while their own official manifests are limited to dnd5e 5.x. For any newly found medium-popularity candidate, perform the recorded upstream manifest/release and target-gameplay check before adding it to the localization queue; no new candidate was selected in this fixed six-module refresh. `Untested`/`NOT_EXECUTED` never means available in the module-health acceptance document.
