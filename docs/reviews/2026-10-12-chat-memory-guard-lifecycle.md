# 聊天内存保护 G1–G3：缓存、运行生命周期与独立说明

## 当前结论

本地源码已修正缓存清理后的旧请求复用、失败来源无界保留、重复注册与停止后异步工作继续等问题，并接入同源只读帮助。模块48项/298断言通过；真实Foundry窗口、聊天历史读回、媒体加载及长时表现仍待验，新候选未安装。用户确认Forge仍使用5.3.3网页，本批仅用合成数据与JSDOM。

## G1缓存归属

旧实现四个反例均失败：clear后同源请求仍指向旧Promise；失败来源一直保留；同步抛错使pending索引滞留；零容量把已回收URL返回给卡片。现在clear清空pending索引并增加代次，Promise完成时只移除自身，不误删新请求；过期结果释放源资源并回收URL。完成项按容量淘汰，零容量返回undefined。

失败来源记忆同样受容量约束，独立失败计数保留实际失败次数并在clear归零。runtime日志只输出固定失败提示，不输出头像路径、URL或原始error。进行中的底层图片请求不是可取消网络任务；这不构成首次原图请求被阻止或全部瞬时内存有硬上限的承诺。

## G2停止、刷新与重新开始

旧实现重复start会注册两组Hook，stop没有退订Hook；过期头像可把宿主已恢复的图片改回默认图，detach/disable期间等待中的裁剪批次也会继续派发下一次删除。四例均先复现，修复后通过。

当前start幂等，记录自有Hook ID与稳定beforeunload回调；stop只移除自己的监听、Observer、timer和缓存。头像按运行代次核对晚到结果。聊天controller可dispose，异步批次在每次后续删除前核对启用状态、挂接身份和设置代次。已经交给Foundry的一次DOM移除可以完成，但旧批次不会继续派发；世界ChatMessage不进入删除接口。

主控另补多窗口反例：刷新期间关闭一个窗口时，要继续刷新其他窗口。独立审阅进一步复现保留数20→22期间旧批次仍删第二张的P2；现在每批捕获runtime generation并逐次核对，该P2经只读复核关闭。测试中世界Map始终22件，DOM只完成已在途的一次移除，剩余21张。

## G3帮助与实际消费者

设置窗口的帮助按钮在GM-only字段组之外，玩家可用且不提交表单。GM仅在Suite active/ABI1有效时调用统一条目，玩家或Suite不可用时阅读模块随包正文。owner docs/manual.json是唯一正文，中央目录仅引用，模块ID与世界/个人设置语义保持。

TokenSync、Resolver和Chat Guard三个实际消费者共用suite-handbook公开的renderModuleManual：输入Document与正文，返回脱离宿主的article。命令与源文本只用textContent呈现，不注册执行按钮，不修改宿主URL、title、存储或DOM。各模块继续负责角色、可选Suite接线与窗口生命周期。源依赖编进各自ZIP，没有新增必须安装的Foundry模块；各owner watch保留并补共享包。
