# DeepSeek 长时间等待：官方规则、真人案例与 Forge 可借鉴部分

日期：2026-10-15。范围：回应“其他人怎么处理的”，只查公开资料和现有代码，不修改冻结版，不再次调用模型。

结论：应区分连接仍在维持、模型开始输出、完整答案收到和真正断线。不能仅凭五分钟没有完整 JSON 就断言服务失败；也不能把超时改成十分钟就算修好。以下外部证据没有证明 Archivist Grim 上一次到底在排队、生成还是传输。

## 对照当前 Forge

- 本次失败收据见 [Archivist Grim V8 单次复验](../acceptance/2026-10-15-forge-archivist-grim-v8-retest.md)：一条基础提取请求在约 300 秒处终止，没有完整模型回复。中文核对、导入和刷新均未执行。
- 冻结的 `.local/forge-archivist-grim-retest-20261015/run-once.ts` 为请求设置了 300 秒外层中止，并在把响应交给正式处理前先等待 `response.clone().json()` 完成。这次只记录了 HTTP 200，未保留逐段到达情况，最后被归为笼统网络失败。
- 当前 `packages/intake-ai/src/transport.ts` 的流式发送和解析仅适用于 `openai-responses`；本轮 DeepSeek 使用 `openai-chat`。因此不能只加一个 `stream: true` 就宣称具备 DeepSeek 流式支持。
- 现有证据不足以区分排队、模型生成慢、真正断线或其他中间层中止。账单和实际消耗也未知；不能认为本地取消就一定没有计费。

## 可落地的候选修复，尚未实施

1. **把等待状态记清楚。** 分别记录请求发出、收到响应头、最后一次收到数据、首次答案文字和完整结束的时间。只记事件、字节数和时间，不保存或展示模型内部推理文字。维持连接的空行只能算连接活动。
2. **把提前中止原因分开。** 区分本地时间限制、主动取消、网络断开、服务端报错、回复未完成和内容无效，不能全部显示“网络请求失败”。核对运行脚本、传输层和生成流程各自的计时，避免一层允许继续、另一层先掐断。
3. **等待期间继续同一个请求。** 已有活动时，提示仍在等待并允许用户取消；确实无活动或超过明确设置时才按对应原因停止。是否调整总时限应有可配置策略及证据，不直接把 300 改为 600 当成修复。所有自动重发继续关闭。
4. **先用离线数据验证。** 若采用流式接收，先适配 `openai-chat`，用本地构造的数据覆盖空行、连接提示、先有推理字段但暂无答案、分段 JSON、截断、取消、结束标记及超时。最终必须收到完整结束并重新解析、核验完整 JSON，不能把半份文字送往 Actor 生成。
5. **保留单次验收的边界。** 用户授权的一次 V8 复验已失败；本调研不构成第二次付费调用授权。冻结版、原首次失败和修复后失败原件均保持，后续真实测试需另有用户指示。

以上是候选方案，未证明本地修复成功，也没有完成完整中文 Actor 的原始目标。
