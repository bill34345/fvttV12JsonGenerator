## 1. 核心判断

**主要瓶颈是把集成状态、测试操作和证据关联留给了长对话中的代理临场处理。** 项目已经有模块边界、纯函数测试、固定构建、混合验收与持久夹具。继续堆规范、换更高 reasoning、增加角色，不能自动补上连续攻击的真实桥接缺口。

本次最值得处理的五件事，按顺序是：

1. 把今天保存的 Vex 两击数据及已经补入的恢复候选修复连到真实复验，把连续命中重新授予列为独立用例。
2. 让既有 harness 自动关联第二击与收据，取消机器已知字段的人肉转抄。
3. 把当前状态与历史叙述分开，恢复时只执行唯一未关闭的门槛。
4. 将局部可独立验收的规范/工具改动从大功能包中拆开评审，减少工作树规则漂移和依赖整合债务。
5. 按完成的工单核算主任务、执行者、返工与用户介入；再决定模型和 effort，而不是用单次调用价格推算节省。

代理执行与工具设计承担主要的直接责任；用户可以改善任务切片和目标优先级，但日志不支持把双方责任机械分成一半。用户要求真实验收、反对重复轮询、要求复用夹具和精简报告，都是合理纠偏。

### 5.1 对用户提示方式的具体建议

不应要求用户给出每个函数、hook 或浏览器点击。代理收到明确目标后，负责查资料、恢复合法工具入口、实施和验证。好的提示只需要压住交付范围与完成标准。

最容易增加成本的是把“完成整个模块”“提速全项目”“修改全局 skill”“研究外部方案”“复盘额度”绑在同一条长线程里，让每次继续都携带所有未结束目标。应把它们视为不同工单；这不要求为每个小步骤新开聊天。同一个故障的诊断→修复→受影响验证保留上下文，不相干的流程实验单独安排。

你也需要在“尽快完成”之外明确主要优化目标：本次最优先是**单位已验收工单的总消耗**，还是主任务 Astra 额度、墙钟时间、最少用户介入。独立 Luna 可能降低主任务负担，但只有计入主/子全部请求与返工才知道总消耗是否降低。此前明确选择独立 Luna 的偏好应保留，不能由代理未经测量来回改默认。

“我要明天完成”可用于排序，不能替代范围决策。代理应该给可关闭的切片和未测风险，不应在首条高风险集成链尚未通过时给无依据完成承诺。

还应直接去掉“300%第一性原理”“至少思考五分钟”这类约束。它们不能给出正确性条件。更有效的要求是：“给出两个竞争解释、各自证据、一个能区分它们的检查；没有证据的写成假设。”不需要更长、更严厉的提示，需要更少且可检查的交付条件。

### 5.2 代理应该承担的改进

- 不把文档生成量、静态测试数量或安装哈希当成交付进展。
- 工具错误先分类为产品、夹具、观测、环境、权限、编排；同一个无新信息的错误不重复打 UI。
- UI 中必须出现的 Activity/Midi Apply/优势选择保留；身份关联、数据提取、批次复位和收据整理由程序完成。
- 一个真实难点由同一实现 owner 负责端到端状态机；审查者可以独立反驳，但不让多个 writer 同时补同一 runtime。
- 长输出保存在证据文件；只返回本轮差异、结论、失败原因和精确引用。避免在父子上下文重复吞页面树、截图、完整 JSON。

## 7. 建议的架构与验证方式

### 7.1 保留三模块职责，缩小跨模块含糊状态

保留 WMP 规则/攻击协调、Conditions 一次性效果生命周期、TE 通用事件。不要因跨模块出错就把所有代码合并，也不引入新的远程服务或通用 DSL。

在 WMP 内明确三个职责：

1. **输入适配：**原生 dnd5e 与 Midi 各自将真实消息/hook 归一为带 attack/source/target 标识的事实；同一次攻击只有一个启动 owner。
2. **状态转换：**处理 prepare/start/命中/应用伤害/commit/cancel，明确 Actor ledger 的权威与内存缓存可重建条件。
3. **观察与判定：**收据从实际事件/文档读回生成，不控制业务成功；通知失败独立记录；测试结果不能反过来强迫业务 ledger 假装成功。

先在现有函数接口上落实返回值与测试，只有第二个真实调用者或明确重复出现才抽公共层。`runtime.ts` 的拆文件应服务可测试边界，不把两千多行本身变成重构任务。

Vex 最小契约为：`firstGrant → nextRollAdvantage → oldEffectConsumed` 与 `nextHitDamageApplied → freshGrant` 两段。miss、取消、到期、错误目标分别覆盖自己的转移，避免把全部排列拖到人工 UI。

### 7.2 验收层级

| 层 | 负责发现什么 | 触发与完成标准 |
|---|---|---|
| 纯规则/状态机 | 资格、参数、预约/消费、取消/到期、幂等 | 修改对应规则或状态转移时；明确反例先红再绿 |
| 实际消息形状 + 依赖桥接 | 原生/Midi 卡结构、两击关联、真实 Conditions 生命周期 | 修改 adapter/共享接口/proof 时；保存实际消息的脱敏最小 fixture，核对未被 mock 掉的部分 |
| 精确 Lab 内真实 API | 持久文档、GM 权威、HP/效果、重载恢复 | 改相关运行路径时；每次使用真实接口和读回，直接写期望效果不能作为通过 |
| 少量真实 UI | Activity 入口、Midi Apply、优势选择、Push 目的地、玩家→GM | 只对不同交互和已知 UI 故障保留；同一类规则组合下沉，不逐条手工重复造夹具 |
| 候选整合 | 当前依赖组合、manifest/产物、支持承诺与手册 | 组合改变或发布前；保留必要完整门槛，历史 PASS 保留原身份 |

上述分层大部分已写进 custom-module-development.md。新增工作是补真实桥接与机器收据、让 gate 按这些条件执行。旧构建 PASS 不改标签冒充新构建；同时也不因为任意文档编辑就使全部历史玩法证据失效。

### 7.3 让 harness 完成机械工作

继续复用现有 GM 面板和 batch API，不另造测试平台。一次运行应自动给出：候选/依赖身份、用例、前置条件、attackId 关联、观察是否齐全、业务子结果、精确失败原因和下一条可执行动作。导出应能通过正常应用入口保存并重载验证；优先修好现有 Copy last / 保存流程，不使用被拒绝协议或其他控制通道绕行。

完整 JSON 留证据目录，模型默认拿紧凑摘要；需要定位时再按 trace/字段读取。场景、Actor、Item、Combat 和初始化工具在批次内保留，用例间复位，串行操作共享世界。

当前 gate 假如是 proof 解析缺失，下一轮只为它添加诊断与回归；不能再从“Chrome 能否打开网页”起步，除非有新的连接失败证据。

## 8. 规范、工作树和模型方案

### 8.1 规范与状态载体

- 产品目标固定为全部功能由自有 mod 实现。上游用于理解 hook 时序、消息关联、优势/消费和伤害处理方式；对照精确版本及许可后适配本项目架构。后续整理旧 ADR，标明当前决策及被替代关系；不再把“参考上游代码”解释为依赖上游模块交付八种功能。
- 根 AGENTS 保留影响权限/正确性的稳定约束；版本路径和执行步骤留 owner/runbook。现有文件并非全部冗余，不提出一刀切删除。
- global AGENTS 管分工/权限原则；仓库负责产品边界；模块负责不变量；runbook 负责命令。遇到相同义务不让代理再执行一次。
- 每个模块仍只有一个主清单、可选一个 active-case。顶端用很短的 current gate 块给出 build、fixture、已完成结果、唯一 blocker、下一动作、停止条件；历史条目标为历史，不与当前命令竞争。
- 已经通过的工具/规范改善在可独立验收时单独准备集成，不等 WMP 十一规则全通过。真正耦合的接口和消费者保持同一个评审增量。
- 建议将“本地 topic checkpoint”“合并 master”“push/发布”定义为可分别授权的阶段。当前规范将 commit 也纳入明确发布授权，这确实使长期未提交增量更难管理；本报告只提出修改方向，不替用户执行提交或改变权限。
- 已有 worktree 不按年龄或数量删除。先记录 active owner、当前任务、是否含未整合成果；长期治理的目标是完成与整合，不是目录数变少。

### 8.2 模型与 effort 的试运行配置

本机当前配置读回为 Astra/max，context 872000、auto-compact 600000；这是配置值，不是所有历史 turn 的有效值。角色文件为 worker/researcher Sol/high、explorer/tester Luna/max、reviewer Astra/low。历史运行模型见聊天审计。

本表按工作类型选择模型，不要求把任务拆给子代理。本次按用户最新要求由主任务亲自完成；今后的委派也应服从当时的明确偏好。核心诊断、耦合实现和最终结论由同一个负责人贯通，不能把角色名称当作质量保证。

| 工作 | 建议起点 | 升级条件 |
|---|---|---|
| 常规主任务：边界、整合、结果复核 | Astra medium | 涉及未解释跨模块状态/竞态时使用 high；max 留给有具体未解假设的难点 |
| 边界清楚的实现与局部回归 | Sol high，保留现有 worker 设置 | 同一故障两次尝试仍无新增证据时，由根做设计诊断，不能无限重派 |
| 路径定位、已定义的数据提取 | Luna medium 作为小规模比较候选 | 复杂关联或遗漏风险才增加 effort；并非本轮直接更改现有 max |
| 普通 Chrome | 若仍明确选择独立执行，沿用可复用 Luna/max；否则由主任务完成 | 真正难的集成步骤由主任务直接判断；不能用低模型价格证明总量节省 |
| 独立审查 | 普通小差异 low/medium；跨模块状态机用 Astra high | 审查输入是差异、契约、反例和证据，而非全量历史重新开题 |

这是待测配置，不宣称 GPT-6 各角色已有本项目受控胜率。固定一个工单期间的模型/effort，以免把改模型、改规范、改工具混在同次实验。也不引用未经本机证实的“切 effort 必定丢缓存”传言。

更大的上下文窗口不是节省策略；600k 自动压缩阈值允许对话累积很久。不要未经试验硬改为某个神奇 token 数。先控制每次返回量与工单边界，完成一个独立交付或切换无关目标时再开新会话，携带短状态包；同一故障的有效历史继续复用。

## 9. 落地顺序和如何证明有效

下列是实施方案，不代表已完成，也不是新增全仓整改平台。

| 顺序 | 工单 | 验收出口 |
|---|---|---|
| P0-A | 对齐当前范围与唯一状态；接住已有 Activity 恢复候选和两击回归，补必要的分支诊断 | 现有修复证据可复核，明确哪些离线 PASS 已有、哪个真实 gate 未关闭；不从头重写测试 |
| P0-B | 单 owner 关闭该候选的真实两击链，完成自动第二击关联和重新授予子用例 | 窄桥接回归通过；精确候选同一原 UI 链证明优势、旧消费与命中后的新授予；不能把手填字段作为常规步骤 |
| P1-A | 打通可保存/重载的紧凑结果和完整收据 | 同 batch 复位后重跑不重新造资源；收据可找回且无需转抄 IDs；一个中断后能恢复到正确 gate |
| P1-B | 对齐当前 master 的 Conditions/生成器与候选；分离可独立集成的规范/工具改动 | 11 个差异路径逐一归属；共享 API 消费者定向检查；按整合节点跑必要完整门槛；发布仍需原有授权 |
| P2 | 其余未测规则按交互类型关闭，再用实际工单比较模型/effort | 已知失败、未执行项与支持承诺分别关闭；得到完整成本分母，不用静态绿代替玩法 |

第一轮只安排一个能在 1–3 小时工程窗口内评估结果的窄切片：**复核已有第二击恢复候选，关闭它的一个真实复验 gate**。这不是承诺三小时内完整发布 WMP。若信息不足，产物应是明确缺失字段和最小采集动作，而不是又一份笼统提速报告。

衡量用“单位合格工单”，不以 token 越少越好：

- 输入、缓存输入、输出、推理分别记录；推理和缓存是子集，不能重复相加。
- 主任务与执行者分别记，再在去重/排除继承基线后汇总；返工、交接、恢复也计入。
- 同时记有效运行时间、环境/用户等待、工具调用、人工介入、首个有用失败时间、是否最终通过及新增回归。
- 先对 3 个实际完成工单建立小基线。若确需模型比较，再选两个固定离线故障、相同验收条件，对两个设置各做两次；这是方向试验，不是统计显著性声明。
- 流程比较先固定模型；模型比较再固定工具和验收。禁止一次同时改四个变量却把收益归到某一个。
- 可预先设试行目标：重复准备/手填降至零、无新信息重复尝试至多一次、用户介入下降；在完成质量不下降前提下，比较中位时间与非缓存/输出用量。百分比收益等实测后再写。

