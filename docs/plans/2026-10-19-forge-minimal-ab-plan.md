## 1. 首轮要回答的问题

- A：当前 Forge 战斗包的能力处理方式。保留现有程序识别与逐能力模型提案，不人为强制它多调用，也不借机优化。

首轮是“整体方案的小样本探路”，同时包含任务粒度、AI职责和输出格式的差异。即使一边更好，也不能单独归因为批大小或 Markdown 格式；不能用三份资料宣布总体可靠性或统计显著。

## 3. 固定模型、参数和候选

- 模型：沿用已有工作档案 `deepseek-flash`；协议 `openai-chat`；`reasoning: low`；同一连接档案、同一账号；不查阅或落盘凭据。此次只选择计划参数，不读取或更改实际连接设置。
- 两侧都用 `json_object` 外壳。A 内容沿用当前事实回复；B 外壳携带 category、整类 MD 字符串及对应 unitId 顺序索引。B 的实际业务结果仍为填好的 MD，不能偷换为另一套纯 facts 提取。
- B 的 MD 只用本候选现有 parser 已支持的键、枚举和结构；模型收到每类空模板与相同的来源规则要求。封装、模板和 MD→共同结构适配需在后续实现时固定哈希，当前没有这个可直接运行的 B 入口。
- 目标统一为 Foundry 14.364 / dnd5e 5.3.3 / core，图标 off；保持来源语言，不要求额外中文翻译。中文来源本身仍须准确理解。
- 程序候选必须等原 chat 出现稳定可用边界后再选定。A/B 在同一固定候选上运行；不能把文档 worktree 的 master 当 Forge 候选，也不复制/提交/冻结原 chat 正在修改的文件。
- 当时固定来源单元、公共验证器、两边提示和模板、模型参数、等待策略与失败分类。A 保留原有能力分流和提取提示；B 使用相同受支持语义要求，不增加示例答案。
- 请求按实际 HTTP 计数；公共基础的保存回复回放不算真实模型调用。回复中的实际 model、finish reason、token 与缓存字段可得时保存，模型身份不一致则保留结果并标对照无效。

## 4. B 每批具体交付什么

程序给出：本类别全部完整能力原文、程序分配的 unitId/名称、所属共享前言、跨能力清单/必要关联原文、对应 MD 模板与支持范围。原始来源仍由程序保存。上下文不能靠另一笔模型请求的隐含聊天记忆传递。

MD 按类别填写，每个能力独立条目，覆盖名称、完整描述、动作类型、攻击/伤害/豁免/治疗、范围与目标、次数/恢复/消耗，以及必要的多操作或子活动与 GM 边界；来源没有的字段省略。模板沿现有 renderer/parser 规范确定，不在本次新发明一套 DSL。原文、位置、来源身份不能由模型回复替换。

未来执行时，程序只解析 B 的 MD 并映射到共同验证出口；不能在背后替 B 补上漏掉的攻击、豁免或时机，再算 AI 成功。来源证据与身份绑定等公共机械工作允许共用并记录。如果适配层无法无损表达原本支持的机制，先标为“B 接口未具备”，不开真实 A/B，也不归咎模型。

B 批次顺序固定为 Actions → Bonus Actions → Traits → Reactions → Legendary Actions → Mythic Actions；空类跳过。本轮后两类均空。不在开跑后改成语义小组或删除困难能力。

对每份结果按以下顺序判断：

1. **完整性**：18 个父能力的身份/去向逐项可追踪；未到达与提取后漏项分开；重复、错类别、漏正文或漏规则均记录。头部/叙事的共同保留也不能退化。
2. **语义正确性**：逐项核对数值、主体、目标、动作时机、成功/失败、条件、期限、次数和消费。明确基础操作不能退成仅文字后算合格；无法自动执行的复杂后果保留完整 GM 边界，不额外要求实现新自动化。
3. **正式候选**：两侧进入同一来源校验与 parser/generation/verifier。保留 B 原始 MD、共同结构和生成候选；区分模型内容失败、模板/适配失败、公共验证器误报、传输失败。共同离线法术解析前置若缺失，应记共同阻塞，不把某侧判为模型失败；本轮不连接 Foundry Resolver 或实际 Cast。
4. **基础保持**：共同八组基础事实在两边结果中保持相同，公共来源补全另记；不得为修能力顺便改 AC、HP、属性、感官或语言。

主结果是：每侧三份来源中有几份首次得到完整正确的能力候选、18 项能力有几项正确/错误/未到达、每个关键错误是什么。严重的错条件/错目标/错误自动化不能被更多普通字段正确抵消；不造一个加权总分掩盖它。

## 7. 速度、费用与评审怎样记录

- 六次运行顺序预先固定为 S1 A→B、S2 B→A、S3 A→B，全部串行，不与原 chat 争用服务。这个小样本顺序不能消除服务端缓存/负载差异；记录缓存 token 和时间窗口，不声称冷缓存公平。
- 分开记录能力阶段墙钟时间、实际模型等待之和、本地解析/验证/生成时间；不包含共用基础准备、翻译、人工核对、适配器开发和安装时间。另记适配器准备成本，避免把它藏掉。
- 每笔实际 HTTP 记录阶段、case/unit/category、尝试数、模型、完成/截断原因、可得的输入/输出/推理/缓存 token；不记录凭据和模型推理正文。价格或账单未核实就只比较用量，不造费用数字。
- 失败 case 不能因提前停止而被评成更快。时间表同时列结果状态；只有同一来源两边都达到相同正确性出口时才比较其成功耗时。
- 原始回复全量保存供追查；语义评审优先看统一后的结果 X/Y 和来源/预期清单，先记错误再揭示 A/B。MD/JSON 的格式差异可能暴露身份，不能宣称完全双盲，也不额外调用 AI 裁判。
- 三对各一次只能发现明显失败和形成下一步线索。若两边都合格、差异小或运行波动明显，结论为“首轮不足以区分”，不更换默认模式。
