## 阶段 B：完成最小可复用能力

先盘点现有入口和差异，只填缺口。对外命令名称在实现阶段根据已有 CLI 确定；下列是分批候选能力，**不是现在已经可运行的命令，也不是首次试用必须全部造齐的前置**。首个消费者优先补预检失败阻止派发、绝对路径／身份绑定、收据读回这几个反复出错的接口；既有 fixture 和清理能力继续使用。

| 能力 | 输入／输出 | 最小完成条件 |
| --- | --- | --- |
| prepare | 任务路径、候选、环境、授权范围 → 规范化合同及前检 | 自动取版本／ID；绝对路径和候选匹配；错误退出会阻止后续派发。 |
| execute boundary | 合同与专属 fixture → 一次正式操作／观察 | 先验证最小真实入口及输出往返；单操作有超时，超时后先读状态，不盲目重放有副作用动作。 |
| collect／classify | 原始事件、文档读回、可见结果 → 不可变原件及独立摘要 | 自动关联 run／case／attack／receipt；不完整与业务失败分开；不支持的语义保留人工判定入口。 |
| resume／cleanup | 当前合同、已接受证据、对象归属 → 下一步及清理回执 | 恢复不重建整批；只处理明确归属对象；callback 父 UUID／dispatchId 可核对并去重。 |

文件侧优先复用 `tools/foundry-ops` 及 WMP `e2e/receipt-cli.ts`、`e2e/receipt-evidence.ts` 的职责；运行侧复用现有 GM 面板与正式公共入口。不得为了实现“一键”绕过 Chrome 工具许可、页面归属或数据操作限制。

每个模块的 adapter 只描述前置对象、正式入口及独立语义判断。共用层不硬编码 Vex／武器名，也不把“没有 console error”当所有业务的 PASS。WMP 保持八种精通和额外特性的自有实现，上游只提供实现参考。

## 阶段 C：随当前增量选择旧失败，不设跨项目总门槛

以下是可选择的真实负例清单。每个增量只选择它实际改变的边界；例如首批选择语法失败派发、错误路径、陈旧／错误收据，再立即进入 D 试用。Item Piles 缓存、迁移清单、视觉和部分写入只在对应消费者需要时加入，不能让首个小任务等待全部完成。审计阶段做了证据映射，**尚未运行这些工具回归**。

| 已发生的负例 | 新能力应怎样失败／恢复 | 所需验证层 |
| --- | --- | --- |
| 宏语法失败但仍 send_message | 不发出任务，准确返回 syntax failure | 文件侧控制流回归；测试派发调用次数为0。 |
| textarea 保存后显示空 | 在最小输出往返发现空／不可解析，业务 case 不开始 | 真实序列化边界加一个界面烟测。 |
| active-case 落在另一 worktree | 路径／身份不匹配时拒绝使用，返回准确目标 | 离线路径与合同检查。 |
| hook 顺序与 mock 相反 | 原错误实现下目标回归失败；更正后通过 | 精确版本契约／已保存事件重放，不只自建 mock。 |
| Reset 递归 merge 留下旧字段 | 复位后读回无旧 case／预约，不把旧快照当当前 | 真实差异／合并语义检查。 |
| Item Piles 先缓存旧集成 | await 模拟不能遮蔽同步 hook 的实际顺序 | 实际注册 API→首次消费→缓存回归。 |
| 85 项遗漏旧世界启用项 | 每个源 ID 有明确去向；未处理差集使“迁完”失败 | 保存清单集合复算，不连接服务。 |
| 旧卡目标快照被当当前输入 | 区分历史消息与本次输入，不设置伪门禁 | 消息协议＋当前前置检查。 |
| 错 callback／旧合同／重复回调 | 精确路由，旧 revision 不覆盖当前，重复结果不重复执行 | 合同及回执检查；跨线程送达只在获准委派时验证。 |
| 截图文件存在但画面不对 | 不升级为 accepted，要求对应对象与步骤的视觉证据 | 人工／获准视觉核对，不能只靠文件名或 hash。 |
| 部分转移成功后整体失败 | 先核对现存数据，精确重置或续作，不整批重放 | 保存读回回归，必要时仅受影响专属 fixture 实机复验。 |

旧原件只读保留。若需提交 fixture，只裁取所需的脱敏事件和字段，保留语义与来源映射；不把完整会话、真实生产目标或世界库搬入仓库。fixture 不修改成“容易通过”的期待输出。

## 阶段 D：在下一件实际工作中试用

选择自然发生、已授权的小集成任务；不人为制造功能或重复已通过的 WMP 来凑指标。当前增量通过所选 C 检查即可开始，不等待整个能力清单完成。先固定 Astra/max 及验收出口，用一个真实链路完成 prepare→操作→收据→恢复／清理。

若新工具需要人工反复修合同、成本超过省下的重复动作，就缩小工具；不能因为已经写了平台而继续维护错误抽象。第一消费者只证明能用；第二个不同消费者验证共用边界，成立后再增加抽象。

浏览器工作按用户当时有效的模型／effort要求和 Chrome 委派规范执行；当前项目普通 Chrome 配置见上面的执行配置，历史同模型／effort要求按对应记录理解。Chrome 完成后由结果事件恢复主控，不搭 watcher 或反复轮询。

## 测量：接受一次合格结果到底付出了什么

每个实际任务记录下面的时间点与数量；可自动取的字段不让模型填写。

- 起点、环境就绪、第一次能定位原因的失败、第一次语义通过、父审接受、清理完成；等待用户／环境与主动工作分别标记。
- 工具／运输失败次数、同一失败无新证据重试数、业务返工数、重建 fixture 次数。
- 人工介入分别记录代理错误纠正、必要产品决策／授权、用户主动范围变化。时间可统计，后两类不算代理返工或坏prompt；范围变化后标明比较边界变化。
- 父子任务的去重逐响应 token：总输入、缓存输入、输出；reasoning 是输出子集。没有账户换算依据就不报金额／额度百分比。
- 已要求的行为、真实接口、角色／持久化与必要界面检查是否全部满足，之后是否发生漏验缺陷。

初期取三个边界相近的实际任务做描述性记录；历史任务不具备同一复杂度与完整计时，不能宣称受控提速百分比。出现语义漏验、错误删除／越权或旧回执被误接受，试点直接失败，先修再评；这些不能用更快完成抵扣。

机械目标可直接验：不再手填工具已知 ID，预检失败不派发，重复回调不重复执行，同类工具错误不触发整批玩法重测。时间／token是否下降由实际数据回答，不预先承诺“节省50%”。
