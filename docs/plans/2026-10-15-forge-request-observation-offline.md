# 请求等待与故障观察：离线修复

授权：修复五分钟直接中止、无法定位等待阶段的问题；仅用离线数据验证，不调用 DeepSeek，不自动重试，保留冻结版及两次失败现场，不提交、合并或推送。

依据：[公开资料与实际案例](../reviews/2026-10-15-forge-deepseek-timeout-and-keepalive.md)。已经核实：五分钟强制中止在旧单次验收脚本；工作台已有人工继续/结束选择。普通 JSON 请求缺少正文接收过程的观察，外层超时原因也可能被泛化成网络错误。

实施顺序：

1. 记录旧冻结模块、冻结清单、验收脚本和失败目录的文件指纹。旧冻结模块继续只读；本轮修改工作树源码形成后续修复，不能把新源码说成原冻结版本。旧验收脚本作为失败原件保留，不能再当新流程入口。
2. 在正式传输入口逐段读取普通 JSON 回复，记录响应头、首段/最后一段数据、字节数、空白连接信号及完整结束。只在完整解析成功后返回内容；不额外开启流式模型协议，不保存推理正文。
3. Forge 默认沿用同一请求继续等待，保持人工取消能力，禁用隐式重发。区分外层超时、主动取消、连接失败、正文中断和无效 JSON；安全状态能用于等待提示和收据，不暴露请求、密钥、模型推理或原始错误。
4. 用保存的失败元数据及本地构造回复验证：越过五分钟仍保持同一请求、连接提示不冒充答案、分段中文完整解析、中断/取消/超时分类、无效内容阻断、每种失败只发一次。再检查受影响消费者、包类型、架构和手册，最后核对保护目录指纹。

检查理由：本次改变共享请求传输、Forge 默认等待和故障信息，所以新增定向离线回归，并运行现有 provider/协议、Forge 消费端及类型门禁。生成规则、来源解析和最终 Actor 投影没有改动，沿用已有来源语义证据，不重放付费或原生验收。

共享影响补查：新的错误分类依赖取消原因，原先 Item、Species、中文和战斗配置的内部计时器没有标注原因，会把内部超时误标为主动取消。因此仅为这些既有计时器增加明确的超时原因，并保留合并信号的原始原因；追加各自已有离线 provider 检查。未改变它们的来源、生成规则、既有总时限或重试策略。首次消费者检查中原先“失败自动发两次”的期望按本任务改为一次；取消检查改为等到正文读取确实开始再取消，消除依赖固定微任务次数的假设。

最终类型检查补充：新增测试的 fetch 替身补齐明确的类型转换；同时补齐上一轮发现回归夹具遗漏的 authMode/reviewModel 配置字段，仍使用假客户端。单独重跑原发现回归，不重跑来源生成或付费验收。

验收边界：本轮只证明离线等待和故障处理符合预期；不能证明 DeepSeek 实际返回、Archivist Grim 完整中文生成或 Foundry 导入刷新成功。完整产品目标保持未完成。
